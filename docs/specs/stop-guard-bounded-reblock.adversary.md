## Verified-safe

- **stop_hook_active=false always forces blocks:1 regardless of stored fingerprint** (G3) — guarantees a genuinely fresh chain-start never inherits a stale count from an unrelated prior chain sharing the same session_id.
- **State file older than 6 hours treated as absent** (G3) — combined with the fingerprint-mismatch branch, closes the "--resume reuses session_id a day later" case in the ordinary (item set actually changed) case.
- **Sorted-list fingerprint input** (G2) — closes an ordering-based instability independent of the serialization issue in #2.
- **G5 bypass unchanged** — `JUDGE_STOP_GUARD=off` semantics untouched by this spec; no new risk introduced there.
- **"No stale items -> delete state, allow"** (G3) — clean terminal state on genuine success, no leftover file to misread next time.

## Blind spots

- Cannot verify, from a read-only pass, whether Claude Code's Stop-hook `systemMessage` field (used for the allow-with-warning yield) is ever surfaced back to the model versus only shown in the human-facing transcript/UI — this single fact determines whether finding #5 is a BLOCKER or a non-issue, and resolving it requires either platform-doc research outside this pass's scope or an empirical harness run.
- Cannot verify whether multiple Stop hooks execute sequentially (each able to see a prior hook's effect within the same cycle) or independently in parallel — this determines whether "stop_hook_active caused by a different hook" (finding #9) can occur on the very same cycle as this guard's own would-be first block, versus only on subsequent cycles.
- One attack I could not construct without running the hook: an actual two-process race performing the read-modify-write on the same session-keyed JSON file on Windows NTFS — I can reason about lost updates and truncated reads structurally, but cannot empirically confirm `fs.renameSync`'s atomicity guarantees under true concurrent access (e.g., destination file open for read by a second process mid-rename) without spawning two real Node processes against the implemented hook and inspecting the resulting file state.
